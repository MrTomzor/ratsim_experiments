====== SLURM - job scheduler ======

RCI cluser uses SLURM as job scheduler. [[https://slurm.schedmd.com/quickstart.html|Official quick start is here]].

Basic commands are:

**''sacct''** is used to report job or job step accounting information about active or completed jobs.

**''salloc''** is used to allocate resources for a job in real time. Typically this is used to allocate resources and spawn a shell. The shell is then used to execute srun commands to launch parallel tasks.

**''sinfo''** reports the state of partitions and nodes managed by Slurm. It has a wide variety of filtering, sorting, and formatting options.

**''squeue''** reports the state of jobs or job steps. It has a wide variety of filtering, sorting, and formatting options. By default, it reports the running jobs in priority order and then the pending jobs in priority order.

**''sbatch''** is used to submit a job script for later execution. The script will typically contain one or more srun commands to launch parallel tasks.

**''srun''** is used to submit a job for execution or initiate job steps in real time. 

**''salloc''** is used to allocate resources for a job in real time. Typically this is used to allocate resources and spawn a shell. The shell is then used to execute srun commands to launch parallel tasks.

**''sattach''** is used to attach standard input, output, and error plus signal capabilities to a currently running job or job step. One can attach to and detach from jobs multiple times.

**''scancel''** is used to cancel a pending or running job or job step. It can also be used to send an arbitrary signal to all processes associated with a running job or job step.

**''sacct''** is used to report job or job step accounting information about active or completed jobs.

If not specified, job will go to ''cpu'' partition. Jobs submitted to partitions with higher priority can overtake jobs submitted to lower priority partitions. E.g. if there are running jobs on node01 from ''cpuextralong'' partition and scheduler will decide to run new job from ''cpufast'' partition on the ''node01'' and there are not enough resources (CPU or memory) some job or jobs from ''cpuextralong'' partition will be preempted and resumed, when job from ''cpufast'' partition will finish or another resource will be freed. 

Nodes are also weighted:  CPU nodes are with the lowest weight, SMP node with middle and GPU nodes with the highest weight. E.g. when job is submitted to the ''deadline'' partition, with no need of GPU or many CPUs, then will be started on the node with the lowest weight and enough resources.

====== Limits ======

To stop the overwhelm of a cluster with single-user tasks, we have applied user limits on the number of allocated CPUs and GPUs. Users from RCI and outside RCI have the limit set differently. The limits are different for each partition. The user’s QOS limits take precedence over  partition limits. If the user’s limit is undefined, partition’s limit will be used. If the user's neither partition’s limit is not defined, there is no limit on resources.
 
A total of 3392 CPUs (1344 Intel, 2048 AMD)  in the cpu queues, 2656 CPUs ( 864 Intel, 1792 AMD) and 104 GPUs ( 48 V100 in Intel and 56 A100 in AMD) in the GPU queues.

It means that RCI members can submit unlimited number of jobs and use max. 1152 CPUs and 32 GPUs in the *fast partitions. But  only 150 jobs or 300 CPUs and 1.5TB of memory and 6 GPUs in the extralong partitions. non-RCI users can run only 100 jobs, use only 250 CPUs, 1TB of memory and only 6 GPUs in any partition.





===== Starting interactive job =====

Interactive jobs are allowed only in the cpufast,gpufast,deadline and gpudeadline partitions,
Basic command for job submission into queue is **''srun''** . 
In the simplest example:
<code>
user@login2:~$ srun -p cpufast --pty bash -i
hostname@n01:~$ hostname
n01
</code>
the new bash will be started on the first free node from partition ''cpufast''.

GPU cards have to be allocated by --gres=gpu:number_of cards, otherwise, job submited into gpu* partition will be rejected.

===== Noninteractive batch jobs =====

It's possible to prepare batch script with multiple commnands.
<code>
user@login2:~$ cat simple.batch
#!/bin/sh
#SBATCH --partition=cpu
#SBATCH --time=1
/bin/hostname
srun -l /bin/hostname
srun -l /bin/pwd
user@login2:~$ sbatch -n4 -w "n[03-04]" -o simple.stdout simple.batch
Submitted batch job 230
user@login2:~$ squeue
             JOBID PARTITION     NAME     USER ST       TIME  NODES NODELIST(REASON)
user@login2:~$ more simple.stdout
n03
0: n03
1: n03
3: n04
2: n04
0: /home/user
1: /home/user
2: /home/user
3: /home/user
</code>
From output, we can view, that batch was started on n03 and then executed on n03 and n04 as requested by ''-w'' switch.

=== sbatch parameters ===

parameters can be specified on command line or in the batch script
<code>
#!/bin/bash

#SBATCH --nodes=1                    # 1 node
#SBATCH --ntasks-per-node=36         # 36 tasks per node
#SBATCH --time=1:00:00               # time limits: 1 hour
#SBATCH --error=myJob.err            # standard error file
#SBATCH --output=myJob.out           # standard output file
#SBATCH --partition=<partition_name> # partition name
#SBATCH --mail-user=email_address    # where send info about job
#SBATCH --mail-type=ALL              # what to send, valid type values are NONE, BEGIN, END, FAIL, REQUEUE, ALL 
</code>

==== Environment variables ====

There are a number of environment variables provided to the SLURM job. Some of them are taken from the user's environment and carried with the job. Others are created by SLURM.

All SLURM-provided environment variable names start with the characters SLURM_.

Below are listed some of the more useful variables, and some typical values taken as an example:

<code>
SLURM_JOB_NAME=job
SLURM_JOB_ID =453919
SLURM_JOB_NODELIST=n01,n02,n[24-30]
SLURM_SUBMIT_DIR=/home/username
SLURM_SUBMIT_HOST=login1
SLURM_CLUSTERNAME=rci
SLURM_JOB_PARTITION=gpu
</code>

There are a number of ways that you can use these environment variables to make more efficient use of SLURM. For example SLURM_JOB_NAME can be used to retrieve the SLURM jobname. Another commonly used variable is SLURM_SUBMIT_DIR which contains the name of the directory from which the user submitted the SLURM job.

Note: $SLURM_JOB_NODELIST will display the node names in contracted forms, meaning that for consecutive nodes you will get their range instead of the full list. You will see in square brackets the ID of the first and the last node of the chunk, meaning that all the nodes between them are also part of the actual node list. If list of nodes is needed use:
<code>
scontrol show hostnames ${SLURM_JOB_NODELIST}
</code> 

==== Serial job example ====

For a typical serial job you can take the following script as a template, and modify it depending on your needs.

The script asks for 10 hours wallclock time and runs a serial application (R). The input data are in file "data", the output file is "out.txt"; job.out will contain the std-out and std-err of the script. Data from home directory are copied to the very fast local scratch storage and job is started here. When finished scratch is removed.

<code>
#!/bin/bash
#SBATCH --time=10:00:00
#SBATCH --nodes=1 --ntasks-per-node=1 --cpus-per-task=1
#SBATCH --mem=10G
#SBATCH --out=job.out
SCRATCH_DIR=/data/temporary/job_${SLURM_JOB_ID}
mkdir ${SCRATCH_DIR}
cp ~/my_data ${SCRATCH_DIR}/ 
cd S{SCRATCH_DIR}
module load R 
R < data > ~/out.txt
rm -rf ${SCRATCH_DIR}
</code>

==== MPI job example ====

For a typical MPI job you can take one the following scripts as a template, and modify it depending on your needs.

The script asks for 8 tasks, 4 nodes and 1 hour of wallclock time, and runs an MPI application (myprogram) compiled with the GCC 8.2 OpenMPI 3.1.3 library (in the [[installed_modules#foss|foss/2019a]] toolchain). The input data are in file "myinput", the output file is "myoutput", the working directory is where the job was submitted from. Through “–cpus-per-task=1” instruction each task will bind 1 physical cpu (core).  
<code>
#!/bin/bash
#SBATCH --time=01:00:00

#SBATCH --nodes=4
#SBATCH --ntasks-per-node=8
#SBATCH --cpus-per-task=1

#SBATCH --mem=18G
#SBATCH --partition=cpu
#SBATCH --job-name=jobMPI
#SBATCH --err=myJob.err 
#SBATCH --out=myJob.out 


ml  foss/2021a
srun --cpu-bind=cores --mpi=pmix myprogram < myinput > myoutput
</code>


===== Resource allocation =====

For SLURM jobs, it's possible to allocate memory, CPUs or GPUs via job parameters.
  * **''-n''** sets how many CPUs = threads should be allocated. Default is 1
  * **''-N''** how many nodes should be used. Default is 1.
  * **''--mem-per-cpu=''** sets how much memory per CPU should be allocated. Default value is 4GB per CPU.
  * **''--mem=''**  sets how much memory for job should be allocated. Default is 4GB * number_of_CPUs_requested
  * **''--gres=gpu ''** - how many GPUs should be allocated. Default is none.
  * **''--exclusive''** - selected node will be whole allocated for job
  * **''-t ''** - how many minutes will should be resource allocated.
  
==== Examples ====
<code>
user@login2:~$ salloc -n32 -p longjobs
salloc: Granted job allocation 197
user@login2:~$ squeue -j 197
             JOBID PARTITION     NAME     USER ST       TIME  NODES NODELIST(REASON)
               197  longjobs     bash     user  R       0:09      1 n01
user@login2:~$ scancel 197
salloc: Job allocation 197 has been revoked.
</code>
32 CPUs = threads (there are 32 available on CPU nodes) have been allocated.

<code>
user@login2:~$ salloc -n32 --mem=500G -p longjobs
salloc: Granted job allocation 198
user@login2:~$ squeue -j 198
             JOBID PARTITION     NAME     USER ST       TIME  NODES NODELIST(REASON)
               198  longjobs     bash     user  R       0:07      1 n33
</code>
Because 500GB memory request, job have been started on n33 (Nodes n01-32 have only 392GB memory, n33 have 1.5TB).

<code>
user@login2:~$ salloc -n32 --gres=gpu:4
salloc: error: Job submit/allocate failed: Requested node configuration is not available
salloc: Job allocation 201 has been revoked.
</code>
Request for 4 GPUs and 32 CPUs has not been successful, because there are no GPUs in default partition ''cpu''. Partition with GPUs have to be specified:
<code>
user@login2:~$ salloc -n32 -p longjobs --gres=gpu:4
salloc: Granted job allocation 202
user@login2:~$ squeue -j 202
             JOBID PARTITION     NAME     USER ST       TIME  NODES NODELIST(REASON)
               202  longjobs     bash     user  R       0:10      1 n21
</code>

<code>
salloc --exclusive -t 60
salloc: Granted job allocation 203
user@login2:~$ squeue -j 203
             JOBID PARTITION     NAME     USER ST       TIME  NODES NODELIST(REASON)
               203       cpu     bash     user  R       0:14      1 n01
</code>
Whole node for 60 minutes has been allocated.

===== Job arrays =====
Job arrays offer a mechanism for submitting and managing collections of similar jobs quickly and easily; job arrays with millions of tasks can be submitted in milliseconds (subject to configured size limits). All jobs must have the same initial options (e.g. size, time limit, etc.).

Job arrays are only supported for batch jobs and the array index values are specified using the **''--array''** or **''-a''** option of the sbatch command. The option argument can be specific array index values, a range of index values, and an optional step size as shown in the examples below. Note that the minimum index value is zero and the maximum value is a **1000**. Jobs which are part of a job array will have the environment variable ''SLURM_ARRAY_TASK_ID'' set to its array index value.
<code>
# Submit a job array with index values between 0 and 31
$ sbatch --array=0-31    -N1 tmp

# Submit a job array with index values of 1, 3, 5 and 7
$ sbatch --array=1,3,5,7 -N1 tmp

# Submit a job array with index values between 1 and 7
# with a step size of 2 (i.e. 1, 3, 5 and 7)
$ sbatch --array=1-7:2   -N1 tmp
</code>

A maximum number of simultaneously running tasks from the job array may be specified using a **''%''** separator. For example ''"--array=0-15%4"'' will limit the number of simultaneously running tasks from this job array to 4.

[[https://slurm.schedmd.com/job_array.html|More information about job arrays]].
